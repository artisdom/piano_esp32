# Test log — 2026-10-15

Live experiments behind `GZUT_piano_protocol.md`. Host: Linux, BlueZ 5.85,
ALSA. Piano on USB as card 3 (`hw:3,0,0`, `/dev/snd/midiC3D0`) and on BLE
as `7E:5F:FA:08:FC:BF`. A person watched the LEDs/display and reported
what they saw; "observed" below is their answer.

Tools: `amidi`, a small Python rawmidi logger (timestamped `os.read` on
`/dev/snd/midiC3D0`), `aseqsend`/`aseqdump`, `busctl` (BlueZ D-Bus
`GattCharacteristic1.WriteValue` with `type=command`), `sudo btmon`.

## C. BLE

GATT dump (`busctl tree org.bluez`, `gattcat read`):

```
service0001 (GAP)   char0002 Device Name → "" , char0004 Appearance → 00 00
service0006 (GATT)
service0007 (03b80e5a-…)  char0008 7772e5db-…  flags read, write-without-response, notify
                          desc000a CCCD;  read value "01234567";  MTU 508
```

C1 — BlueZ MIDI plugin path (ALSA seq client 128 "GZUT-MIDI Bluetooth"):

* `aseqdump -p 128:0` received key presses fine (same velocity set).
* `aseqsend -p 128:0 '90 3C 01'` → no LED (two attempts, 8 keys more).
* D-Bus `WriteValue` on the characteristic → "Operation Not Authorized"
  (characteristic claimed by the plugin), also after pairing.
* btmon showed what the plugin actually transmits:

```
ATT: Write Command  Handle 0x0009  Data b8f2903c01
ATT: Write Command  Handle 0x0009  Data 88c6803c00
ATT: Write Command  Handle 0x0009  Data 82b0903c01   (C4)
                                        85a8903e01   (D4)
                                        889e904001 … 96ec904801
ATT: Write Command  Handle 0x0009  Data acd2903c01 … 818b904801
```

None of these 16 Note Ons lit an LED.

C2 — raw GATT writes (bluetoothd restarted as transient unit with
`-P midi`; normal service restored afterwards):

| # | Packet                                         | Observed            |
|---|------------------------------------------------|---------------------|
| E1 | `80 80 90 3C 01`                              | C4 lit              |
| E1 | `82 B0 90 40 01`                              | E4 **not** lit      |
| E1 | `80 81 90 43 01`                              | G4 lit              |
| E2 | `80 B0 90 41 01`                              | F4 lit              |
| E2 | `82 80 90 45 01`                              | A4 **not** lit      |
| E3 | `80 80 90 15 01 16 01 … 6C 01` (179 B)        | all 88 lit; `80 80 B0 7B 00` cleared all |
| E4 | `80 80 90 3C 01 80 90 40 01 81 43 01`         | C4, E4 lit; G4 not  |

Conclusion: header byte must equal `0x80`; remaining bytes are parsed as a
plain MIDI stream (timestamp bytes act as status bytes — `81 43 01` is a
Note Off for G4).

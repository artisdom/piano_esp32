# ESP32-2432S028R "Cheap Yellow Display" (2.8″, ESP32) — hardware reference

Board directory `2432s028`. Written 2026-10-17 from the firmware, the repo
docs, the bench logs of the 2026-10-16 sessions and the vendor pack
(copied to [`vendor/2432s028/`](vendor/2432s028/)). Labels used below:
**code** = what the firmware drives (verified to work on the bench unit);
**schematic** / **spec** / **datasheet** / **demo** = vendor material only,
not exercised by Piano Coach unless stated.

## 1. Summary

The ESP32-2432S028R ("Cheap Yellow Display", CYD) is a 50 × 86 mm display
board from Shenzhen Jingcai Intelligent: an ESP32-WROOM-32 module (4 MB
flash, no PSRAM), a 2.8″ 240×320 TFT on SPI with a 4-wire resistive touch
film read by an XPT2046, a CH340C USB-UART behind a micro-USB socket, an
RGB LED, a light-dependent resistor, a microSD slot, an 8002-class speaker
amplifier on the DAC pin and three small JST-style 1.25 mm connectors.
Piano Coach runs its **mini** UI on it in landscape (320×240, drawn at
1.25×), keeps 776 songs in a flash song pack and reaches the piano over
the ESP32's native BLE only. The speaker, LDR, microSD and RGB LED are not
used (the LED is driven off).

## 4. Subsystems

### 4.1 Power

* 5 V comes from the micro-USB V+ through D1 (1N5819W Schottky) or from
  P1 pin 1 (VIN) through Q1 (AO3401 P-MOSFET, gate to GND: reverse-polarity
  protection) (schematic).
* Two AMS1117-3.3 regulators: U7 makes **3.3V-ESP** for the module only;
  U1 makes **3.3V** for the LCD, touch, microSD, RGB LED, LDR divider,
  speaker amp and the CH340C. Each has a 0 Ω jumper (JP3, JP0) drawn
  across Vin–Vout; whether they are fitted is unknown (schematic).
* No battery, no charger, no software power switch. `power_off()` turns the
  backlight off and enters deep sleep with ext0 wake on GPIO0 low; it first
  waits for BOOT to be released so the press that chose "Sleep" does not
  wake it at once. RST also wakes (it resets) (code). The LCD, touch
  controller and LED stay powered in deep sleep (they hang on the always-on
  3.3V rail; schematic).

### 4.2 USB, CH340 and auto-reset

* CH340C (U6) on 3.3V, USB D+/D− to the micro-B socket; its TXD drives
  U0RXD (GPIO3), RXD takes U0TXD (GPIO1) (schematic). Console: UART0,
  115200 baud (ESP-IDF default, `CONFIG_ESP_CONSOLE_UART_BAUDRATE=115200`
  in the generated sdkconfig),
  `cpu_start: GPIO 3 and 1 are used as console UART I/O pins` (boot log).
* Auto-reset is the usual cross-coupled pair (schematic): T1 (S9013) base
  ← RTS# via R12, emitter ← DTR#, collector → GPIO0; T2 base ← DTR# via
  R14, emitter ← RTS#, collector → EN. So asserting RTS alone resets the
  chip, asserting DTR alone pulls GPIO0 low, and espflash's sequence enters
  download mode without touching the keys.
* For log capture open the port with DTR and RTS **de-asserted** (pyserial:
  set `dtr = False` and `rts = False` before `open()`),
  else the board resets or stays in reset; reset deliberately with an RTS
  pulse (AGENTS.md, bench practice).

### 4.3 Display

* **Controller.** The spec says ILI9341; the LCD module datasheet
  (JC2432B028N, V1.0 2022-06-16) says ILI9341V, SPI, 240×RGB×320, 4 LED
  backlight (15 mA × 4 at 3.2 V). The firmware does not trust either: it
  creates the panel with esp_lcd's **ST7789 driver** (both controllers take
  the same MIPI DCS commands for reset, sleep-out, MADCTL, COLMOD, CASET/
  RASET, RAMWR), then reads RDDID (0x04) and picks a power/VCOM/gamma table:
  ID `000000` → its ILI9341 table, anything else → its ST7789V table (from
  ESP-IDF's spi_master/lcd example).
* **What the bench unit does (code wins):** every bench log reads
  `lcd: ID 180606 → ST7789`, so on this unit the **ST7789V table**
  (`B2 B7 BB C0 C2 C3 C4 C6 D0 E0 E1`) is sent, and the display is verified
  correct with it. "ST7789" in that log line is only the name of the branch,
  not an identification of the controller: what `18 06 06` means, and why
  it differs from the WROVER-KIT's `000000`, is unknown. AGENTS.md calls it an "ILI9341-class panel (reads ID
  18 06 06)". The ILI9341 table has never been applied on this board; the
  ESP-WROVER-KIT's ILI9341 does read `000000` (its log, same code path).
* **Bus.** SPI2 (HSPI) on its own IOMUX pins — SCK 14, MOSI 13, MISO 12,
  CS 15 — so 40 MHz works without the GPIO-matrix limit; D/C on GPIO2;
  mode 0; 8-bit commands and parameters; DMA (`SPI_DMA_CH_AUTO`); largest
  transfer 320 × 10 × 2 bytes; transfer queue depth 4 (code). MISO is
  wired only to read the panel ID.
* **Reset.** The panel's RESET (P2 pin 2) is on the module's EN net, so it
  resets with the chip; the firmware passes `reset_gpio_num = -1`, calls
  `esp_lcd_panel_reset` (software reset 0x01) and waits 120 ticks (120 ms
  at 1 kHz) before reading the ID (code, schematic). The vendor's TFT_eSPI
  `User_Setup.h` defines `TFT_RST 12`, which contradicts the schematic
  (GPIO12 is the panel's SDO); the firmware follows the schematic.
* **Orientation.** Landscape 320×240 with the **USB connector on the left**:
  `swap_xy(true)` + `mirror(false, true)` (MADCTL MV + MY). The bench unit
  needs no per-unit mirroring, so `LCD_MIRROR = None` and the mini UI
  offers no "Mirror display" setting (only one unit tried).
* **Colour.** RGB565, 16 bpp, element order **BGR**; pixels are byte-swapped
  in place before each band transfer (`SpiLcd::draw`); no colour inversion
  is set (code).
* **Rendering.** Slint's software renderer draws line bands into
  internal DMA-capable RAM, no framebuffer; UI scale 1.25 (logical 256×192)
  because the mini UI's bar layout is designed for 170 rows (code).
* **Backlight.** GPIO21 → Q2 AO3402 gate (R10 10 kΩ pull-down, so off
  while the pin floats at reset) → LED cathodes via R11 3.9 Ω; anode on
  3.3V (schematic). **Active high**; LEDC low-speed timer 0 / channel 0,
  10-bit, 20 kHz; brightness 0–100 % with a floor of duty 40/1023 above 0;
  boot brightness from NVS `brightness` (default 80, clamped 10–100)
  (code). The vendor's `User_Setup.h` agrees (`TFT_BL 21`, `TFT_BACKLIGHT_ON
  HIGH`).

### 4.4 Touch (XPT2046)

* The XPT2046 (U3) sits on its own pins, not on the LCD's SPI bus: DCLK 25,
  DIN 32, DOUT 39, /CS 33, /PENIRQ 36 with R3 10 kΩ pull-up; VCC, IOVDD
  and VREF on 3.3V (schematic). The pins are not an SPI host's IOMUX set
  and a touch read is a few dozen bits per frame, so `board/xpt2046.rs`
  **bit-bangs** it with plain GPIO (code). The vendor's ESP-IDF demo
  (`5_2_XPT2046_Touch_Test/components/XPT2046/include/xpt2046.h`) uses the
  same pins.
* GPIO36 and 39 are input-only without internal pull-ups; the firmware
  configures them as plain inputs (PENIRQ has the external pull-up).
* **Read sequence** (code): return None unless PENIRQ is low; CS low;
  Z1 (`0xB1`) and Z2 (`0xC1`), pressure `z = z1 + 4095 − z2`, below
  `Z_MIN = 350` = no touch; else one discarded `0x91` sample, three `0xD1`
  ("X") and three `0x91` ("Y") samples, each reduced to the mean of the two
  closest; finally `0xD0` (power down, PENIRQ re-enabled) and CS high.
  Each conversion: 8 command bits, then 16 clocks, result = bits 14..3.
  (The vendor demo uses 0x90/0xD0 commands — different power-down bits,
  same channels.)
* **Calibration** (code, `src/board/2432s028/mod.rs`), "measured on the
  bench unit (taps at the four corners and the centre, extrapolated to the
  edges)". In the USB-left landscape orientation the controller's 0x91
  channel runs along the screen's x axis and the 0xD1 channel along y,
  both **falling**:

  | Screen axis | Raw channel | Raw at 0 | Raw at the far edge |
  |---|---|---|---|
  | x (0…320) | 0x91 ("Y") | 3750 | 230 |
  | y (0…240) | 0xD1 ("X") | 3795 | 340 |

  Mapping: `(raw − at0) × n / (atn − at0)`, clamped to `0…n−1`. The raw
  values and the mapped point are logged at debug level (`touch: raw …`).
  Re-measure on another unit if taps land off target; resistive films vary.
* **Gestures** (mini UI, shared with the round board): tap = press/release
  within 14 px and 700 ms; horizontal swipe right > 40 px = back; vertical
  swipe = scroll about one row per 40 px (code). Which gestures were tried
  on the CYD is not recorded beyond "touch ✔".

### 4.5 RGB LED

MHP5050RGBDT, common anode on 3.3V, each cathode through 1 kΩ to GPIO17
(R16), GPIO4 (R17) and GPIO16 (R20): **active low** (schematic). The
firmware sets all three as outputs high in `early_init` (LED off) and
never lights it (code). Which colour sits on which GPIO is **unknown** —
neither the schematic nor the vendor demo `3_3_LED` names the colours.

### 4.6 Speaker amplifier (not used)

U5 is drawn as **SC8002B**; the datasheet in the vendor pack is the
**FM8002A** (same SOP-8 pinout: 1 SHUTDOWN, 2 BYPASS, 3 +IN, 4 −IN, 5 VO1,
6 VDD, 7 GND, 8 VO2). On this board (schematic): VDD 3.3V; SHUTDOWN tied
to GND, so the amplifier is **always on** (FM8002A: high = shutdown);
BYPASS and +IN on C7 1 µF; −IN fed from GPIO26 through R4 4.7 kΩ, C11
1 nF to GND, R7 47 kΩ, C12 100 pF to GND, C10 0.39 µF and R8 22 kΩ;
feedback R9 68 kΩ from VO1 to −IN (FM8002A gain formula 2 × Rf/Ri =
2 × 68/22 ≈ 6.2). VO1/VO2 go to P4 (bridge-tied: do not ground either
speaker wire). GPIO26 is DAC1. The vendor's buzzer demo toggles GPIO26
as a digital pin. Piano Coach builds this board with `HAS=` (no
`speaker`), so the synth is not compiled in (board.env).

### 4.7 Light sensor (not used)

GPIO34 (ADC1, input-only) sits on a divider: R15 1 MΩ to 3.3V, R19 1 MΩ
to GND with the GT36516 LDR (R21) in parallel to R19 (schematic). The
vendor demo `3_10_adc` reads it with `analogRead(34)`. Direction of the
reading versus light is not documented (unknown).

### 4.8 microSD (not used)

SPI wiring (schematic): CS GPIO5, MOSI/CMD GPIO23, CLK GPIO18, MISO/DAT0
GPIO19; RN2 10 kΩ pull-ups on CS, MOSI, MISO and DAT1; R13 10 kΩ pull-up
on DAT2; card power from 3.3V; the card-detect pin is not connected.
These are the VSPI IOMUX pins, a bus separate from the LCD's HSPI.
The firmware does not mount it (`HAS=` has no `sd`; songs come from flash).
`sdkconfig.defaults` still sets FatFs LFN options because the shared
ESP-IDF checkout carries the exFAT patch, which needs LFN to compile.

### 4.9 BOOT key

GPIO0 with R2 10 kΩ pull-up, to GND when pressed (schematic). It is the
mini UI's only key (`board/key.rs`, polled every UI frame, ≤ 40 ms):
25 ms debounce, tap (reported after the 280 ms double-tap window), double
tap, hold ≥ 600 ms. Footer hint: "tap ›  2× ‹  hold OK" (code). Holding
it during reset enters download mode (strap). It also wakes deep sleep
(ext0, GPIO0 is an RTC pin).

### 4.10 Radio (BLE)

* NimBLE central only, BLE-only controller (`CONFIG_BTDM_CTRL_MODE_BLE_ONLY`,
  one connection, 2 bonds, preferred MTU 260, no security), host task stack
  5 KB, NimBLE log level WARN (sdkconfig.defaults). The piano link uses the
  `80 80` + plain-MIDI framing described in AGENTS.md.
* **TX power +9 dBm.** The original ESP32 defaults to +3 dBm; `ble_midi.rs`
  sets `ESP_PWR_LVL_P9` for DEFAULT, SCAN and CONN_HDL0 (`cfg(esp32)`)
  because this board saw the piano at −83 dBm a couple of metres away
  (code comment). After that the bench runs logged −59…−65 dBm.
* **`ble_relaxed`** (set by `build.rs` for every `MCU=esp32` board and every
  headless board): connect at 30–50 ms interval with a **10 s** supervision
  timeout (`SUPERVISION_10MS = 1000`); when the piano renegotiates to 10 ms
  / 500 ms, ask once more for 30–50 ms / 10 s (at most twice per
  connection); answer the piano's update requests with the same floor;
  wait for the CCCD write's answer before streaming; gather 15 ms of MIDI
  per write (`WRITE_GAP`). Observed sequence (2026-10-16 log): 50 ms / 10 s
  at connect → piano 10 ms / 500 ms → request → back to 50 ms / 10 s. The
  10 s timeout was chosen because a hand between this weak-antenna board and
  the piano blanked the link for over 4 s (code comment).
* **UI on core 1.** `threads::spawn_core1` pins the UI thread to core 1 on
  the original ESP32: the BT controller and NimBLE host run on core 0, and a
  busy UI there (plus the LCD's SPI interrupts, which follow the core that
  opened the panel) starved the link (code comment).
* **Host flow control OFF (`CONFIG_BT_NIMBLE_HS_FLOW_CTRL=n`) — the root
  cause of the drops.** ESP-IDF turns NimBLE host flow control on for the
  original ESP32 only. With it, the controller stopped handing the piano's
  packets to NimBLE once it had sent as many as NimBLE has ACL buffers
  (`transport_pool_acl 24/24` in the logs): the buffer credits never came
  back. Symptoms (run 1, flow control on, 2026-10-16 19:45): the piano's
  key-press notifications stopped about 1 s into playing after 17 of them
  (~24 ACL packets counting MTU / discovery / CCCD answers); the host's ACL
  pool never went below 22/24 free, no write stalls, no NimBLE reset; the
  link dropped with reason **0x208** (supervision timeout) 10.45 s after the
  last notification, and every reconnect then failed with "MIDI
  characteristic discovery timed out" (and once `connect failed (status 0xd)
  … reason 0x216`) until the board was reset. Run 2 (flow control off,
  otherwise identical): 14 minutes of Follow with both hands and song changes
  from the piano, 1869 notifications in, 6167 writes out, no drop, no busy
  retries, RSSI about −60 dBm (commit a7c4765). Things tried before that and
  ruled out: RSSI, LCD SPI speed, NimBLE pool sizes, modem sleep, FreeRTOS
  in flash.
* Kept from those experiments because the board was verified with them:
  `CONFIG_BTDM_CTRL_MODEM_SLEEP=n`, NimBLE's default buffer pools (not the
  WROVER-KIT's trimmed 12/12), FreeRTOS and ring-buffer functions in IRAM.
* Diagnostics in `ble_midi.rs` (all boards): a periodic traffic line
  (writes, notifications, busy retries, RSSI), on a drop or failed connect
  how long ago each direction last moved plus every NimBLE mempool
  (free/total, low-water mark), write stalls over 500 ms, and NimBLE
  self-resets (`reset_cb`).
* The piano accepts one BLE connection at a time: power other boards or the
  tablet app off while testing this one.

## 5. Memory map and partitions

### Partition table (`boards/2432s028/partitions.csv`)

| Name | Type | SubType | Offset | Size | Content |
|---|---|---|---|---|---|
| nvs | data | nvs | 0x9000 | 24 KB (0x6000) | prefs (namespace `piano`, i32), best scores, NimBLE bonds |
| phy_init | data | phy | 0xF000 | 4 KB | RF calibration |
| factory | app | factory | 0x10000 | 0x280000 (2.5 MiB) | firmware |
| songs | data | undefined (0x06 in the boot log: "Unknown data") | 0x290000 | 0x170000 (1.44 MiB) | song pack (`tools/songs.sh`) |

The bootloader and partition table sit at 0x1000 / 0x8000
(`CONFIG_BOOTLOADER_OFFSET_IN_FLASH`, `CONFIG_PARTITION_TABLE_OFFSET` in the
generated sdkconfig; ESP-IDF defaults). The table ends at
0x400000 = 4 MB exactly. App image on the bench (commit 3cb28a4 build,
sum of the `esp_image` segments): 2 316 392 bytes (2.21 MiB) of the
2 621 440-byte (2.5 MiB) factory partition. Song pack: `target/2432s028/songs.bin` 1 394 177 bytes of
1 507 328; the firmware logs "pack of 1247 entries, 776 songs, 1361 KB".

### Song pack budget (`SONGPACK_ARGS`)

`--max-bytes 1400K --max-notes 1200 --prefer 儿时回忆（41） --prefer
红色歌谣（52） --prefer 影视剧场（240）`: small categories first, then songs
until 1.4 MB, none with more than 1200 notes. The 1200-note limit is the
same as on the ESP-WROVER-KIT and the ESP32-C3 board (internal RAM only).
`boards/2432s028/glyphs.slint` is generated by `tools/songs.sh 2432s028
build` from this pack (776 songs, 1344 distinct characters); rebuild the
firmware if it changes.

### RAM

* No PSRAM: everything lives in the ESP32's internal SRAM. At boot,
  `heap_init` reports DRAM regions of 0 + 7 + 16 + 109 + 14 (D/IRAM) + 111
  (D/IRAM) KB plus 28 KB IRAM, before Bluetooth starts.
* With BLE, the UI and a song loaded (bench log): heap free 128 KB (minimum
  119 KB, largest block 108 KB); 131 KB free after loading a 155-note song;
  UI thread stack (`ui_mini::STACK` = 14 KB) with 7–9 KB left.
* `piano-core` was made to fit (commit 3cb28a4; no-PSRAM boards crashed
  on long songs in Follow): engine timeline entries are 8 bytes (u16
  target index) — a 1200-note song in Follow has 4800 of them; exact
  capacity, in-place unstable sort with an explicit tie order, the old
  timeline freed before a rebuild; song notes sorted in place; SMF events
  pre-sized instead of grown by doubling.
* Threads: player 12 KB (`spawn_ext`, a plain spawn on this board), UI 14 KB
  pinned to core 1, main task 8 KB, pthread default 6 KB, NimBLE host 5 KB.

### Notable sdkconfig settings (`boards/2432s028/sdkconfig.defaults`)

| Setting | Why (from the file's comments / commits) |
|---|---|
| `CONFIG_ESPTOOLPY_FLASHMODE_DIO`, `FLASHSIZE_4MB`, custom `partitions.csv` | WROOM-32, 4 MB; song pack partition |
| `CONFIG_ESP_DEFAULT_CPU_FREQ_MHZ_240` | no comment in the file (maximum clock) |
| `CONFIG_FREERTOS_HZ=1000` | "MIDI timing needs ms resolution" |
| `CONFIG_ESP_MAIN_TASK_STACK_SIZE=8192` | no comment here; same value as the WROVER-KIT, where a 4 KB main stack overflowed on this Xtensa chip |
| `CONFIG_PTHREAD_TASK_STACK_SIZE_DEFAULT=6144`, `CONFIG_ESP_TASK_WDT_TIMEOUT_S=15` | thread default; watchdog margin |
| `CONFIG_SPIRAM=n` | "No PSRAM on the WROOM-32 module" |
| `CONFIG_SPI_FLASH_ROM_IMPL=y` | no comment in the file (ESP-IDF option: use the ROM's flash driver) |
| FreeRTOS / ring buffer **not** moved to flash | "the Bluetooth controller calls them from its real-time paths" |
| `CONFIG_BTDM_CTRL_MODE_BLE_ONLY`, `BLE_MAX_CONN=1`, NimBLE central + observer only, `MAX_CONNECTIONS=1`, `MAX_BONDS=2`, `MAX_CCCDS=4`, `ATT_PREFERRED_MTU=260`, `NVS_PERSIST`, `SECURITY_ENABLE=n`, `LOG_LEVEL_WARNING` | "BLE only (no Classic BT memory), NimBLE central, one link, lean pools" |
| `CONFIG_BT_NIMBLE_HS_FLOW_CTRL=n` | the BLE drop fix, §4.10 — "with flow control the link died ~1 s into playing (17 notifications); without it, 14 minutes of Follow and ~1900 notifications without a drop" |
| `CONFIG_BTDM_CTRL_MODEM_SLEEP=n` | tried against the drops before flow control was found; "kept because the board was verified with them" |
| `CONFIG_FATFS_LFN_HEAP`, `MAX_LFN=255`, `USE_LABEL` | microSD unused, but the shared ESP-IDF's exFAT patch needs LFN to compile |

`board.env` also builds `i-slint-core`, `i-slint-renderer-software` and
`piano-coach` at `opt-level="s"` ("4 MB flash: build the renderer for
size").

## 6. Build, flash, console

```bash
cd firmware/piano-coach
tools/board.sh 2432s028 build --release                 # first build compiles ESP-IDF (10+ min)
tools/songs.sh 2432s028 build                           # pack + boards/2432s028/glyphs.slint
tools/board.sh 2432s028 run --release -- --port /dev/ttyUSB0   # flash.sh: espflash flash --monitor
tools/songs.sh 2432s028 flash --port /dev/ttyUSB0 --baud 921600   # pack → 0x290000
```

Direct espflash (what the sessions used), with
`T=target/2432s028/xtensa-esp32-espidf/release`:

```bash
espflash flash --chip esp32 --port /dev/ttyUSB0 --baud 921600 \
  --bootloader $T/bootloader.bin --partition-table $T/partition-table.bin $T/piano-coach
```

* `tools/board.sh` sources `board.env` (`FEATURE=board-2432s028`,
  `MCU=esp32`, `TARGET=xtensa-esp32-espidf`, `TOOLCHAIN=esp198`,
  `FLASHER=espflash`, `UI=mini`, `HAS=` empty), points
  `ESP_IDF_SYS_EXTRA_COMPONENTS_FILE` at `esp-idf-components.toml` (no BSP;
  only the `src/bindings.h` header as module `bsp`, for the NimBLE / LCD
  APIs), uses `sdkconfig.2432s028` and `target/2432s028`, finds the
  `esp198` clang for bindgen, and exports
  `ESP_IDF_GLOB_PARTTABLE_BASE` for the custom partition table.
* `build.rs` turns `UI=mini` into `cfg(ui_mini)`, and `MCU=esp32` into
  `cfg(ble_relaxed)`; `board::xpt2046` is compiled only for
  `feature = "board-2432s028"`.
* Flashing the firmware does not erase the song pack or NVS; flash the pack
  once after a fresh board or a pack change.
* **Port identification:** `udevadm info -q property -n /dev/ttyUSBx | grep ID_`
  shows the CH340's vendor/model (1a86:7523); a unique serial string was
  not checked on this unit (CH340s usually have none). With several CH340/CP210x boards plugged in, use
  `espflash board-info --port …` and compare the MAC (ec:64:c9:8a:2a:a0).
* **Download mode:** automatic via DTR/RTS (§4.2). By hand: hold BOOT, press
  and release RST, release BOOT. The vendor guide says to "reset the power"
  of the device before uploading again if it does not enter flashing mode.
* **Reset behaviour:** RTS pulse = reset; opening a terminal that asserts
  DTR/RTS resets or holds the board. The LCD resets with the chip (EN).
  Boot log starts `rst:0x1 (POWERON_RESET),boot:0x13 (SPI_FAST_FLASH_BOOT)`.
* **Set a pref from the PC:** NVS image at 0x9000, size 0x6000 (see
  AGENTS.md "set a pref from the PC"); it replaces all prefs and BLE bonds.

## 7. Piano Coach support

* **UI class:** mini — wheel menu over the flash pack, song menu (Learn /
  Follow / Listen, hands, tempo), settings, play screen; BOOT key and touch
  as input; piano-key remote (`piano_core::controls`). `CAPS`: name
  "ESP32-2432S028", backlight yes, power latch no (Sleep = deep sleep,
  "BOOT or RST" wakes), BLE yes, USB no, buttons yes, touch yes.
* **Verified on hardware** (bench unit, ESP32 rev 3.1):
  * 2026-10-16 (commit 3cb28a4): display, touch,
    776-song pack, boot into Follow with a random 儿时回忆 song that starts
    when the piano connects.
  * 2026-10-16 (commit a7c4765): BLE under two-way traffic — run 1 with host
    flow control on dropped as in §4.10; run 2 with it off held 14 minutes
    of Follow, both hands, song changes from the piano, 1869 notifications
    in / 6167 writes out, no drop, RSSI about −60 dBm. The piano's song keys
    were used in those runs (with the folder stepping of that time).
* **Not verified on this board:** the full remote key set (E1/F1 by
  category, G#1 shuffle and its automatic next song, tempo / mode / hand
  keys); the touch gesture set in detail; Settings → Sleep and wake; the
  latest firmware (commits after a7c4765) was built for all boards but not
  re-tried on the CYD.
* **Not supported / limits:** no speaker, microSD, RGB LED, LDR use;
  bookmarks (C8) do nothing on mini boards; no search, A–B loop or sheet
  view on mini boards; songs over 1200 notes are left out of the pack; 776
  of 2449 songs fit.

## 8. Quirks and lessons learned

* **BLE on the original ESP32 needs `CONFIG_BT_NIMBLE_HS_FLOW_CTRL=n`.**
  Keep it in every ESP32 (not S3/C3) profile. The drop looks like an RF or
  load problem (silence, 0x208, failed rediscovery) but is a stalled HCI
  ACL credit loop; the ACL pool logging is what exposed it (§4.10).
* The panel's RDDID is not `000000` on this unit, so the ST7789V table
  runs on what the vendor calls an ILI9341(V). It works; if a future unit
  shows wrong colours or contrast, check the logged ID first (§4.3).
* The panel reset is EN: there is no way to reset the LCD without
  resetting the chip — use the DCS software reset.
* Landscape with the USB connector on the left needs MV + MY; the touch
  axes are swapped relative to the controller's X/Y names and both run
  backwards.
* GPIO36/39 (touch PENIRQ/DOUT) and 34/35 are input-only with no internal
  pull-ups; `key.rs` skips pull-up setup for 34–39 on Xtensa.
* GPIO21 is both the backlight gate and P3 pin 1; anything wired to P3 pin 1
  fights the backlight PWM.
* Strapping pins in use: GPIO0 (BOOT), GPIO2 (LCD D/C), GPIO5 (SD CS),
  GPIO12 (LCD SDO; MTDI must be low at reset for the 3.3 V flash), GPIO15
  (LCD CS). The bench unit boots normally (`SPI_FAST_FLASH_BOOT`).
* The P1 connector's "TXD2/RXD2" pins are UART0 (shared with the CH340
  through 100 Ω), not UART2.
* The speaker output is bridge-tied (VO1/VO2): never ground one side.
* The spec's PCB render (p.6) shows refdes `P5` and `USB3` that are not on
  the V0.1 schematic and slightly different dimensions (outline 49.923 ×
  86.100 mm, holes 41.952 × 78.435 mm apart) from `Dimensions.png`
  (42.0 × 78.0 mm): it may show another board revision. Trust the bench
  unit over either when they disagree.
